# Tovant

A trust-first marketplace connecting car owners with verified independent mechanics, mobile technicians, and detailers. Pilot market: Minneapolis–St. Paul, MN.

**Full design document:** [`design/DESIGN_DOCUMENT.md`](design/DESIGN_DOCUMENT.md) — read this before implementing anything. It covers user flows, the full data model, system architecture, security design, payments/escrow architecture (including exactly what is and isn't real yet — e.g. no payment has ever actually been charged), the design system, and a competitive-gap analysis against category leaders (Angi/Thumbtack/TaskRabbit-style platforms) intended for AI-assisted comparison work. This file is a condensed index of the decisions already made, not a replacement for it — keep both in sync when either changes. **Not yet reconciled** with the roadmap below — see [`design/ROADMAP.md`](design/ROADMAP.md) §5.

**Post-launch roadmap:** [`design/ROADMAP.md`](design/ROADMAP.md) — the follow-up work scoped after the design document's gap analysis (in-app notifications, real payment charging, a visible dispute path, a two-tier "Community Pro" verification track, admin audit-log UI, and more), broken into independently-shippable phases with a live status column. Read this before picking up any of that work — the "## Post-launch roadmap" section below is only a pointer to it, not a duplicate.

**Mockups:** `design/mockups/` (`home.html`, `provider-profile.html`, `provider-dashboard.html`) — `home.html` is still the live source of truth for `src/app/home.css` (see "Design system" below). `provider-profile.html`/`provider-dashboard.html` were the original dark-palette references for `src/app/providers/[id]/page.tsx`/`src/app/provider/dashboard/page.tsx` before both were migrated onto the unified sage-green system — kept for historical reference only, no longer current.

## Non-negotiable product decisions

These came out of an explicit requirements pass with the user — don't silently change them without checking in:

- **Roles:** car owner, provider (unifies mechanic, detailer, and upgrades/fabrication — difference is `provider_categories`, not account type), admin. Upgrades/fabrication (custom exhaust, fabrication, and similar specialized modification work) was flagged as a needed third category early on; categories are no longer a fixed enum (see "Admin-editable taxonomy" below), so adding it is now an `/admin/settings` action, not a migration.
- **Service model:** hybrid — providers can be mobile, shop-based, or both.
- **Verification:** full verification required before a provider can list at all — identity (Stripe Identity), license, insurance, background check (Checkr), plus a separate category-specific credential for each specialty (EV, motorcycle/powersports, commercial/fleet). No self-attested tier.
- **Monetization:** per-lead — a provider is charged as soon as an owner sends them a direct quote request, regardless of whether the provider responds, accepts, or the job happens. Exact pricing (flat per lead vs. variable by category/specialty) is not yet decided; this superseded an earlier flat-rate monthly subscription decision.
- **Job payments:** provider's choice per job — in-app via Stripe Connect Express (manual-capture, functions as escrow) or off-platform (tracked in-app for record-keeping, no funds movement).
- **Escrow release:** hybrid — owner can manually confirm to release immediately, or it auto-releases 72h after the provider marks a job complete if no dispute is opened.
- **Quote flow:** direct request to one provider, not open bidding.
- **Scheduling:** request + manual confirm, not a live-availability instant-book calendar.
- **Cancellation:** free within a configurable window (default 24h), late fee after.
- **No platform guarantee** at launch beyond verification + dispute mediation — providers carry their own liability insurance.
- **Auth:** email/password only — **no 2FA.** Mandatory TOTP 2FA was tried and then explicitly reversed: most users don't have an authenticator app (some don't have a smartphone at all), and the app doesn't need Fort-Knox-level auth even with payments in play. If stronger auth is ever wanted later, prefer something that doesn't require an app (e.g. an emailed one-time code) over reintroducing TOTP.
- **Notifications:** email + SMS + in-app (Twilio + Postmark/SendGrid), reserve a shape for push ahead of the native app.
- **Fleet/business accounts:** out of scope for v1 — individual owners only.
- **Platform:** responsive web first (Next.js). Native apps are Phase 2, not v1.

## Design system

**One design language, app-wide** — sage-green, light by default with a persisted dark toggle, serif display headlines, pill-shaped nav/active states. Originally the homepage-only look (ported ~verbatim from `design/mockups/home.html`); now covers every route (sign-in/sign-up, owner/provider/admin dashboards, `/discover`, public provider profiles, `/become-a-provider`) since there's no real functional reason for the app to run two visual languages, and no dashboard mockup ever existed to justify the old dark palette as a deliberate separate choice. Only `src/app/globals.css`'s own legacy `@theme` block (kept defined but unreferenced everywhere else — see below) remains of the old system.

**Tokens & shared classes** live in `src/app/home.css` (`--home-*` custom properties + `.home-btn`/`.home-nav`/`.home-card`/`.home-table`/`.home-badge`/`.home-input` etc.), imported once from the root layout (`src/app/layout.tsx`) so any route can use them. Rules are scoped under a `.home-page` wrapper class via `:where()` so they carry zero specificity — a route that doesn't render that class is completely unaffected, which is what makes a large multi-phase migration safe to ship incrementally: **a route is "migrated" exactly when its layout/page wraps its content in `className="home-page"` and swaps its markup to the new tokens/classes**, and not a moment before. `src/components/dashboard/portal-shell.tsx` is the standard way a dashboard route opts in (sidebar + mobile tab bar + the `.home-page` wrapper, all in one). Un-migrated routes keep using the legacy dark tokens in `src/app/globals.css` (`--color-void/graphite/steel/ash/ignition/ember`) exactly as before — **that file's `@theme` block must stay defined, not be deleted, until every last page has been migrated**, or every still-dark page breaks at once. Grep `src/` for `bg-graphite|bg-void|text-ash|text-steel|text-ignition|border-steel|bg-ignition|from-ignition|to-ember` to see what's left to convert; once that's zero, delete `globals.css`'s `@theme` block and its `body{}` override as the final cleanup step.

Theme state is global (`HomeThemeProvider`/`useHomeTheme` in `src/components/home/theme-toggle.tsx`, `localStorage` key `tovant_theme`, `data-home-theme="dark"` on `<html>`) — a blocking script in the root layout applies a saved dark preference before paint so there's no flash of light mode. It's `next/script` with `strategy="beforeInteractive"` (**never** a raw `<script>` tag, which triggers a "script tag while rendering" warning) rendered as a **sibling inside `<body>`, not inside a manually-written `<head>`** — Next.js injects `beforeInteractive` scripts into the real HTML head regardless of where the component sits in the tree, and the manual-`<head>`-wrapper version of this (tried once, reverted) re-triggered the same warning under Turbopack dev. `<html>` carries `suppressHydrationWarning` because that script sets an attribute outside React, so a hydration diff on that one element is expected and intentionally silenced — don't remove it, and don't add `suppressHydrationWarning` to new elements to paper over an unrelated bug.

Browser password managers/autofill (Chrome's built-in one, 1Password, etc.) inject style/icon attributes onto form fields before React hydrates — a real, unavoidable hydration-mismatch class with nothing to do with app code, and worth recognizing on sight since it looks alarming (a failed hydration discards and client-regenerates the whole tree, which can surface as an unrelated-looking secondary warning elsewhere, like the script one above). `Input`/`Textarea`/`Select` (`src/components/ui/field.tsx`) all carry `suppressHydrationWarning` on the underlying form element for exactly this reason; `SiteFooter`'s newsletter email input/button carry the same flag standalone since they predate the shared primitives.

**Account menu** (`src/components/home/account-menu.tsx`): the profile chip shown in every public-facing nav bar (`SiteNav` on `/`, `PublicHeader` everywhere else) — hovering (or focusing, for keyboard/touch) it reveals the *same* nav items as that user's dashboard sidebar, resolved via `getNavItemsForRole(role, leadsCount)` from `portal-nav.ts`, plus a Log out action. This means a signed-in owner/provider/admin can reach every dashboard section from anywhere on the site, not only from inside the dashboard itself. `src/components/home/public-header.tsx` is the non-homepage counterpart to `SiteNav` — same logo/nav/theme-toggle/account-menu shell, but `BubbleNav` in `mode="route"` (real links: Home/Find a Pro/For Providers) since these pages don't have the homepage's scrollable sections. Profile lookups for both (`displayName`/avatar/leads-count) go through `src/lib/account-display.ts` so the query isn't duplicated per nav component.

**Migration status**: complete — every route (sign-in/sign-up, owner/provider/admin dashboards, `/discover`, public provider profiles, `/become-a-provider`) is on the unified system. `globals.css`'s legacy `@theme` block is the only thing left of the old palette, kept defined-but-unreferenced per the safety rule above; deleting it (and confirming the grep in that rule comes back empty) is the one remaining cleanup step, not yet done.

Signature motif across the whole app: an **instrument-cluster gauge** (`src/components/ui/gauge.tsx`, a 270°-sweep SVG ring starting at 135°) used everywhere a rating/score would normally be a star row — this is the one recurring visual idea, don't dilute it by also introducing star ratings elsewhere. Defaults to `--home-tint-line`/`--home-accent`; takes `trackColor`/`fillColor` overrides for the rare case a call site needs something else (e.g. on-photo placement) without forking the component.

Type: a serif display face for headlines (`--home-font-serif`), a humanist sans for body text (`--home-font-body`/`--home-font-label`), and a monospace face for prices/VINs/stats/ratings (`--home-font-mono` — the "digital readout" detail that reinforces the instrument-cluster idea). Currently system-font stacks only — real fonts will replace those values later, no component should ever reference a font name directly.

## Stack

Next.js (App Router) + TypeScript + Tailwind v4, PostgreSQL (Neon for local/dev) + **Drizzle ORM** (decided over Prisma), **better-auth** for auth (email/password only — see "Auth" above), S3-compatible object storage for verification docs/media, Stripe (Billing + Connect Express + Identity), Checkr, Postmark/SendGrid + Twilio, Leaflet/OpenStreetMap for maps, Vercel hosting. Package manager is **pnpm**; testing is **Vitest** (unit/integration) + **Playwright** (e2e). All third-party integrations (Stripe/Checkr/Twilio/Postmark/S3) are built behind stub-by-default adapters (`src/lib/integrations/`) since no real test-mode credentials exist yet — real ones slot in later via env vars with no call-site changes.

## Working conventions

- This is a security-sensitive app (payments, background checks, ID documents). Never log or store raw verification documents/PII beyond what's needed — object storage with signed URLs, DB holds references and status only.
- Every appointment/quote/message endpoint needs a row-level ownership check (requester is the owner, the provider, or an admin) — this is a repeated pattern across the whole API, not a one-off. Use the shared helper in `src/lib/security/ownership.ts`, don't reimplement per-route. A full pass over every dynamic `[id]`-parameterized route and every form action taking an id-shaped field (jobs, quotes, vehicles, messages, verification documents) confirmed this is consistently applied — none of them trust a client-submitted user/owner/recipient id without checking it against the session first (e.g. `requestQuote` silently drops a submitted `vehicleId` that doesn't belong to the requesting owner rather than using it).
- Admin actions that touch money or verification status must write to an append-only audit log via `src/lib/security/audit-log.ts`, in the same DB transaction as the mutation. Provider gallery-photo moderation is a deliberate exception — it's neither money nor verification status, so it's tracked via per-row `reviewedByAdminId`/`reviewedAt` on `provider_gallery_photos` instead.
- The homepage (`/`) is session-aware — `SiteNav` (`src/components/home/site-nav.tsx`) queries the session and renders an account chip (avatar-or-initial + first name, linking to the right dashboard) in place of Log in/Get Started when signed in. This makes `/` a dynamically-rendered route (confirmed in build output: `ƒ` not `○`), which is an intentional tradeoff for showing per-user state, same as `/discover`'s existing `force-dynamic`.

## Finding & viewing a provider

Finding a pro and viewing their profile is **public** — no account required (`/discover`, `/providers/[id]`). Only the actions that follow (requesting a quote, messaging) require an owner login, checked inside the server action itself, not just at the route level. `/owner/discover` and `/owner/providers/[id]` are now thin redirects to the public routes, kept so old links don't break.

`/discover` (`src/components/discover/discover-results.tsx`) filters on category, specialty, service mode, minimum rating, a free-text keyword match (business name + bio + offering labels), and location: a "Near" field geocodes whatever the owner types (ZIP or city) via `src/lib/geocoding.ts::geocodeAddress`, then filters/sorts by great-circle distance (`src/lib/geo.ts::distanceMiles`) against each provider's own geocoded coordinates. Provider coordinates come from `profiles.lat`/`.lng`, populated by `src/lib/profile/actions.ts::updateProfile` geocoding the address on save — **only when the saving user's role is `provider`**, since an owner's home address has no current use for coordinates and shouldn't be sent to a third party by default. The homepage hero search (`src/components/home/search-card.tsx`) forwards its service + location fields into `/discover?category=…&near=…`, which the discover page reads server-side and hands to `DiscoverResults` as initial filter state (auto-geocoding `near` on mount).

Geocoding uses OpenStreetMap's Nominatim — free and keyless, so unlike Stripe/Checkr/Twilio/Postmark/S3 (`src/lib/integrations/`) it has no stub/live split and is live from the start; it's not registered in `src/lib/integrations/registry.ts` for that reason. The request is scoped to `countrycodes=us` (`src/lib/geocoding.ts`) because a bare ZIP code is otherwise ambiguous worldwide — e.g. `55101` (Saint Paul, MN) also resolves to a real postcode in Jonava, Lithuania with nothing else to disambiguate it — which matters since the pilot market is US-only anyway. Nominatim's public-instance usage policy caps traffic at roughly 1 request/sec and wants an identifying User-Agent; fine for today's call volume (a human saving a profile or submitting a search), but a self-hosted or paid geocoder should replace it before any real production traffic.

Reviews (`reviews` table) are eligible once a job reaches `completed` or `disputed` — `disputed` covers work that was attempted but went wrong before completion, which was an explicit edge case in the original ask. One review per job (not per provider), editable indefinitely by its owner-author. `providerProfiles.ratingAvg`/`ratingCount` recompute on every review write inside the same transaction (see `src/app/owner/jobs/[id]/actions.ts`) — never on read.

Owners keep a reusable "My Garage" vehicle list (`vehicles` table, managed at `/owner/settings`) that quote requests can reference; providers list what they offer from the admin-editable service-offering taxonomy (`/provider/settings`) and upload "recent work" photos there too, which stay private until an admin approves them at `/admin/gallery`.

The provider dashboard (`/provider/dashboard`) is the leads inbox — its nav (`PortalShell`, see "Design system") links out to the already-real Calendar/Jobs/Earnings/Reviews/Messages pages rather than duplicating them inline. Per-lead charging is real: `src/app/providers/[id]/actions.ts::requestQuote` charges the provider via `leadBillingProvider.chargeLead` (`src/lib/integrations/stripe/lead-billing.{stub,live}.ts`, registered in `registry.ts` the same way as every other Stripe adapter) the instant the quote row is created, for `site_settings.per_lead_fee_cents` (admin-editable at `/admin/settings`, default $15.00) — regardless of whether the provider ever responds, per the documented monetization rule. Every charge is recorded in `lead_charges` (one row per quote, `status: 'charged' | 'failed'`) whether or not the underlying Stripe call is live. Live billing charges the provider's `providerProfiles.stripeCustomerId` off-session — there's still no UI flow that collects a provider's payment method, so live-mode charges fail loudly (`status: 'failed'`) rather than silently no-op until that's built.

An owner accepting a `quoted` request (`/owner/jobs`, `acceptQuote`) is what actually creates a `jobs` row and its `payments` row — this is the only path a job can come into existence today. For `in_app` jobs this now calls `connectProvider.authorizePayment` for real (manual-capture hold) rather than simulating the state. The provider then advances it through a real kanban board (`/provider/jobs`: scheduled → confirmed → in_progress → completed); marking a job `completed` captures the hold (`connectProvider.capturePayment`) and sets `payments.autoReleaseAt` to +the configured escrow window (`escrow_auto_release_hours` in `site_settings`, default 72h, admin-editable at `/admin/settings`). Release is genuinely hybrid now: the owner can hit "Release payment now" on `/owner/jobs/[id]` (`releaseEscrowNow`), or `POST /api/cron/release-escrow` (bearer-token-authenticated via `CRON_SECRET`, meant to be hit by an external scheduler — no queue/cron system lives in this repo) sweeps every payment past its `autoReleaseAt`. Both paths funnel through the one shared `src/lib/payments/escrow.ts::releaseEscrow` helper (capture-then-transfer, audit-logged as `payment.escrow.release`, notifies both parties) so they can never drift, and both refuse to run while the job has an open dispute (`hasOpenDispute`).

Disputes are real too: `openDispute` (owned by the owner, `/owner/jobs/[id]`) freezes the job (`status: 'disputed'`) and blocks any escrow release without touching the payment's own `authorized`/`captured` state, so the admin resolution queue at `/admin/disputes` (`resolveDispute`) knows whether it still needs to capture before it can move money. Four resolutions: release (full amount to provider), refund (full amount to owner), split (partial transfer + partial refund — `ConnectPayoutsProvider.capturePayment`/`.releaseToProvider`/`.refund` all take an optional `amountCents` now, used for exactly this), and close (no financial action, just restarts the auto-release clock). Every resolution is audit-logged (`dispute.resolve`) and notifies both parties.

Late cancellation is real: `cancelJob` (`/owner/jobs/[id]`) is free inside `job.cancellationWindowHours`, and past it charges `site_settings.late_cancellation_fee_percent` (default 20%) of the quoted amount — for `in_app` jobs this captures only the fee portion from the existing authorization and transfers it to the provider (the uncaptured remainder releases back to the owner's card on its own, which is how Stripe's manual-capture partial-capture behaves); for `off_platform` jobs there's no held money to move, so the fee is informational only and collected by the provider directly. Owner-initiated only — a provider-side no-show/cancel path doesn't exist yet.

`providerProfiles.acceptingLeads` (provider's own pause switch) is intentionally separate from `isListable` (system-computed verification/subscription eligibility) — never conflate the two. `providerProfiles.hourlyRateCents` and `.profileViewCount`, `providerUnavailableDates`, and `quotes.paymentMode` are the other schema additions backing the fleshed-out dashboard (profile completeness meter, insights panel, calendar availability, provider's per-job payment-mode choice).

Messaging (`/owner/messages`, `/provider/messages`) is real, not a stub: `src/lib/messaging/threads.ts::getMessageThreads(userId)` groups the `messages` table into per-quote/per-job threads (grouping key is `quoteId ?? jobId`, since that's what a message row is actually attached to — there's no generic "conversation between two users" concept), and `src/lib/messaging/actions.ts::sendMessage` derives the recipient from the referenced quote/job's `ownerId`/`providerUserId` via `requireOwnership` rather than trusting a client-submitted recipient id. Both messages pages also accept a `?quoteId=`/`?jobId=` query param to deep-link into a thread that doesn't have any messages yet (rendered as an empty thread with just a compose box) — this is how "Message" buttons elsewhere in the app (owner's quote/job cards, the provider dashboard's leads panel) start a first conversation; there's no separate "new message" compose flow outside that context.

In-app notifications are real: the `notifications` table (`src/db/schema/notifications.ts`) and `src/lib/notifications/notify.ts::notifyUser` (takes a raw transaction, so it's a plain server-only helper, never a `"use server"` action itself — the client-facing read/mark-read API lives separately at `src/app/notifications/actions.ts`) are wired into every event ROADMAP Phase 4 named: new lead, quote response, payment released, review received, verification decided, dispute opened/resolved, job completed, job cancelled. `NotificationBell` (`src/components/dashboard/notification-bell.tsx`) renders in both `PortalSidebar` and `PortalMobileBar`, polling every 30s — no websocket/SSE infra exists, so this is deliberately poll-based. Email/SMS dispatch for the same events is still a reserved-but-unbuilt follow-up, same as before.

Password reset and email verification are real, both via better-auth's built-in core (`src/lib/auth/auth.ts`: `emailAndPassword.sendResetPassword`, `emailVerification.sendVerificationEmail`), sending through `emailProvider` (stub-by-default, same as every other integration). `/forgot-password` → `authClient.requestPasswordReset` → `/reset-password?token=...` → `authClient.resetPassword`. Email verification is deliberately **not** an access gate (`autoSignInAfterVerification: true`, no `requireEmailVerification`) — a user can use the app before verifying, consistent with CLAUDE.md's low-friction auth stance (no mandatory 2FA either); it's sent on signup (`sendOnSignUp: true`) purely so a user has a way to confirm their address if they want to.

## Accounts, provider onboarding, and admin

Becoming a provider is a two-step, one-way flow. `/become-a-provider` (top-level route, deliberately outside the `/provider/*` route group so an `owner` can actually reach it) is the application form; submitting it flips `role` from `owner` to `provider` in the same transaction that creates `providerProfiles`/`providerCategories`/`providerSpecialties` and, if consent was given, a `pending` background-check `verificationRecords` row — this is the one reviewed role-mutation path in the app, matching the `input: false` on better-auth's `role` field. `/provider/onboarding` (inside the real `requireRole("provider")` gate) is the read-only-until-resubmit status view afterward, showing each verification document's state with an upload form for anything not yet `approved`. Session cookie caching is off (`session.cookieCache` omitted in `src/lib/auth/auth.ts`) specifically so this role flip is reflected on the very next request, not up to 5 minutes later.

Account settings (display name, avatar, address, phone) are shared between owners and providers via `src/components/settings/profile-settings-section.tsx`, rendered at the top of both `/owner/settings` and `/provider/settings`. Backed by the `profiles` table (`src/lib/profile/actions.ts`) and served publicly (no auth/ownership gate — unlike gallery photos or verification docs, avatars are meant to be visible anywhere a name shows) via `/api/avatars/[userId]/image`. Email changes are out of scope for now — would need better-auth's own change-email + re-verification flow, and Postmark is still stub-by-default.

Admin user management uses better-auth's built-in `admin` plugin (`src/lib/auth/auth.ts`) rather than a hand-rolled ban system — it ships `banUser`/`unbanUser`/`listUsers` and revokes sessions immediately on ban. **Must keep `defaultRole: "owner"` set explicitly** in the plugin config — its own create-user hook defaults to `role: "user"` otherwise, a value nothing else in the app (`dashboardPathForRole`, `requireRole`) understands. Banning/unbanning does *not* go through the audit log (`/admin/users`, `src/app/admin/users/actions.ts`) — it's neither a money nor verification-status action, the same documented exception category as gallery-photo moderation.

Admin provider verification (`/admin/providers`, the review queue; `/admin/providers/[id]`, per-record approve/reject) is now real and is the *only* place `providerProfiles.isListable`/`.overallVerificationStatus` get written — `src/lib/providers/verification.ts::recomputeProviderListability(tx, providerId)` runs inside the same transaction as every approve/reject, so the two can never drift. A provider becomes listable only once every required record (`identity`, `license`, `insurance`, `background_check`, plus one `specialty_credential` per row they hold in `providerSpecialties`) is `approved` — this includes `background_check`, which has no uploaded document (Checkr is still stub-by-default) but is still admin-approvable directly, same as any other record. Both actions call `writeAuditLog` with the already-reserved `provider.verification.approve`/`.reject` actions, unlike the ban/gallery exceptions above.

### Admin-editable taxonomy and business rules

`provider_category`, `provider_specialty`, and `service_offering` are no longer Postgres enums — they're admin-editable lookup tables (`src/db/schema/taxonomy.ts`: `provider_category_types`, `provider_specialty_types`, `service_offering_types`), managed at `/admin/settings` under "Taxonomy" (`src/app/admin/settings/taxonomy-actions.ts`). Every dependent column (`provider_categories.category`, `provider_specialties.specialty`, `verification_records.specialty`, `provider_service_offerings.offering`, `quotes.category`) is a plain `text` FK into the matching lookup table rather than a `pgEnum`, with the existing enum values migrated in as seed rows (`drizzle/0006_sour_talisman.sql`, `drizzle/0007_rich_newton_destine.sql`) so no data was lost. Entries are deactivated, never deleted (`active` boolean) — an existing provider's already-selected row keeps rendering with its real label everywhere (`src/lib/service-offerings.ts::getServiceOfferingLabelMap`, `src/lib/taxonomy-labels.ts::getCategoryLabelMap`/`getSpecialtyLabelMap`, and the equivalent joins elsewhere), it just disappears from new-selection checkboxes. This is deliberately scoped to these three *taxonomy* enums only — every state-machine enum (`job_status`, `quote_status`, `payment_mode`, `escrow_status`, `dispute_status`, `verification_status`, `verification_type`, `gallery_photo_status`) stays a hardcoded `pgEnum`, since adding a new state there requires matching code changes everywhere regardless of how it's stored.

`service_offering_types` carries a `categoryId` FK into `provider_category_types` (`drizzle/0009_brainy_wrecking_crew.sql`, backfilled from the pre-existing offering set — e.g. `brakes`→`mechanic`, `exterior_detailing`→`detailer` — so this shipped as a real migration, not a nullable-forever column) — offerings are no longer one flat list shared by every category. Adding a genuinely new task type (tint installers, mobile tire repair, etc.) is a two-step admin-only flow with no code change: add the category at `/admin/settings`, then add each of its offerings there too, each one now required to pick which category it belongs to. `src/lib/service-offerings.ts::getActiveServiceOfferingsForCategories(categoryIds)` is what scopes a provider's own `/provider/settings` Services picker (grouped by category, with a heading per category) to only the categories they've actually selected, instead of showing every offering across every category to every provider.

The two hardcoded timing numbers an earlier audit flagged (escrow auto-release, default cancellation window) are now the `site_settings` key-value table, read via `src/lib/site-settings.ts::getSiteSettingHours(key)` and edited at `/admin/settings` under "Business rules" (`src/app/admin/settings/taxonomy-actions.ts::updateSiteSetting`). `provider/jobs/actions.ts::advanceJob` and `owner/jobs/actions.ts::acceptQuote` both read the live value at the moment they act rather than relying on the `jobs.cancellation_window_hours` column default — this is intentionally a small, scoped key-value table for exactly these two settings, not a speculative generic config system.

### Pilot category scoping — mechanics/mobile mechanics only

The Minneapolis–St. Paul pilot is scoped to the `mechanic` category only (which already covers both shop-based and mobile service via `providerProfiles.serviceMode` — "mobile mechanic" isn't a separate category). Detailing and upgrades/fabrication exist in the taxonomy but are marked `comingSoon` — a second boolean on `provider_category_types`, independent of `active` (`active=false` means "fully retired, FK-only"; `comingSoon=true` means "real row, just not open to owner discovery yet"), toggled at `/admin/settings` alongside the existing active toggle. `comingSoon` categories: don't appear as clickable cards on the homepage (`src/components/home/category-grid.tsx`, now a DB-backed query rather than a hardcoded array) or in the hero search bar's service dropdown (`src/components/home/search-card.tsx`, categories passed down from `src/app/page.tsx`) — both render/omit based on the same query; are excluded from `/discover`'s category filter entirely; but **stay selectable** at `/become-a-provider` (labeled "(Coming soon)") so interested detailers/fabricators can still apply and be ready when the category opens. Already-listed providers under a coming-soon category (e.g. the seeded Lakeside Detailing Co) keep rendering normally on their own `/providers/[id]` page and still appear in `/discover`'s default "all categories" view — `comingSoon` only closes the *discovery entry points* (homepage, hero search, discover filter), not direct links or the unfiltered listing, matching the taxonomy system's existing rule that already-selected rows never break.
